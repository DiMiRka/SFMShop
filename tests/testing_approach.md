# Подход к тестированию в проекте SFMShop

## Обзор

Тесты проверяют бизнес-логику, права доступа, API endpoints и связи между компонентами.
Ни один тест не обращается к реальным PostgreSQL, Redis, RabbitMQ, MongoDB или внешним HTTP API, поэтому весь набор
выполняется за несколько секунд локально и в CI без поднятой инфраструктуры.

Запуск с отчётом о покрытии:

```powershell
.\.venv\Scripts\python.exe -m pytest --cov=src --cov-report=term-missing
```

Результат: 67 тестов пройдены, общее покрытие `src` 93%.

## Принципы

- **Без внешних сервисов.** Репозитории, кэш, очередь и HTTP-клиенты заменяются моками или фейками,
  FastAPI-зависимости подменяются через `app.dependency_overrides`.
- **Тест на баг сначала падает.** Каждый тест, добавленный вместе с исправлением, проверялся на старом коде:
  без исправления он должен падать. Так тест действительно ловит регрессию, а не проходит всегда.
- **Права доступа проверяются через HTTP.** Правила доступа тестируются запросами к реальным маршрутам,
  а не только вызовами функций: так проверяется и подключение зависимостей, и коды ответов.

## Карта тестов

| Файл | Что проверяет |
|------|---------------|
| `test_models.py` | Доменные модели `Product`, `User`, `Order`: создание, расчёт стоимости, скидки и доставки |
| `test_main_order_service.py` | Создание заказа в `OrderService` на `MagicMock`/`AsyncMock`: успешный сценарий, пустой заказ, падение БД без отправки события |
| `test_services.py` | Сервисы товаров, пользователей и заказов на фейковых репозиториях: ошибки, чужие заказы, действия админа, деактивация, смена пароля, баланс с копейками |
| `test_permissions.py` | Права доступа через HTTP: товары и список пользователей только для админа, чужой профиль, поля только для админа, смена своего пароля с `current_password` |
| `test_api.py` | Маршруты FastAPI: список товаров, создание заказа, чужой заказ → 404, пустой список заказов → `[]`, ошибка 500 без деталей для клиента |
| `test_repositories_clients_api.py` | Репозитории поверх фейковой сессии, клиент курсов валют (повторы и переключение провайдеров), `PaymentClient`, делегирование роутеров в сервисы |
| `test_unit_core.py` | JWT и хэширование паролей, схемы Pydantic, дескрипторы и миксины, `CacheService`, обработчики исключений, длина email в схеме и в БД |
| `test_integration_wiring.py` | Сборка зависимостей, `get_current_user`, lifespan приложения, middleware логирования, продюсер и консьюмер очереди, генераторы сессий БД |
| `test_utils.py` | `ExchangeRateClient` с `patch("...httpx.AsyncClient")`: клиент вызывается с ожидаемыми параметрами |

## Ключевые сценарии безопасности

Эти тесты защищают от уже найденных и исправленных уязвимостей:

- чужой заказ нельзя увидеть или удалить, при попытке не меняются ни баланс, ни склад, ни очередь событий;
- заказ всегда оформляется на текущего пользователя, `user_id` из тела запроса игнорируется;
- обычный пользователь не может менять товары, читать чужие профили и менять `balance`, `is_active`, `is_admin`;
- свой пароль меняется только с верным `current_password`, в том числе для админа;
- деактивированный пользователь не может войти, обновить токен или пользоваться уже выданным токеном;
- при ошибке 500 клиент получает общее сообщение, а исключение с traceback попадает в лог.

## Техники

### Фикстуры

Общие фикстуры в `tests/conftest.py`:

- `sample_product`, `sample_user`, `sample_order` для доменных моделей;
- `log_messages` собирает сообщения loguru во время теста, чтобы проверять логирование без перехвата stdout.

### Параметризация

Используется для расчётной логики и для матрицы прав доступа: один тест проверяет несколько маршрутов
или ролей.

```python
@pytest.mark.parametrize("method, url, body", [
    ("post", "/v1/products/", PRODUCT),
    ("put", "/v1/products/1", {"quantity": 2}),
    ("delete", "/v1/products/1", None),
])
def test_only_admin_can_change_products(method, url, body):
    ...
```

### Моки и фейки

- `MagicMock` и `AsyncMock` для точечных проверок вызовов (`assert_awaited_once`, `assert_not_awaited`);
- фейковые репозитории в `test_services.py` хранят состояние в памяти: после вызова сервиса можно проверить,
  что именно изменилось у пользователя, товара или заказа;
- `HttpClientFake` возвращает заранее заданную последовательность ответов и исключений, так проверяются
  повторы и переключение между провайдерами курсов валют;
- `app.dependency_overrides` подменяет сервисы и текущего пользователя в API-тестах.

### Негативные сценарии через side_effect

```python
order_rep.create.side_effect = RuntimeError("DB error")
```

Так проверяется, что при падении БД событие в очередь не отправляется.

### Особенности

- В Starlette 1.0 `app.debug` — обычный атрибут, а стек middleware кэшируется при первом запросе.
  Тест ошибки 500 сбрасывает `app.middleware_stack`, чтобы результат не зависел от `DEBUG` в локальном `.env`.
- Для проверки 500 используется `TestClient(app, raise_server_exceptions=False)`, иначе исключение
  пробрасывается в тест вместо ответа.

## Покрытие кода

Инструмент: `pytest-cov`. Общее покрытие `src`: 93%.

Полностью покрыты роутеры `src/api/v1`, проверки прав `src/core/permissions.py`, схемы, репозитории,
`exchange_client` и `product_service`. Сервисы заказов и пользователей покрыты на 98%.

Наименее покрытые модули:

- `src/services/queue_consumer.py`: 54%, не покрыты объявление exchange и очередей и обработка сообщений
  (`process_cache_event`, `process_notification`);
- `src/services/queue_producer.py`: 67%, не покрыты создание singleton, ошибка подключения и повторы публикации с backoff;
- `src/services/log_service.py`: 79%, не покрыты `critical` с отправкой алерта и настройка Sentry при заданном DSN;
- `src/database/connection.py`: 80%, не покрыт откат транзакции при ошибке.

Обработку сообщений и повторы публикации можно покрыть на моках, это следующий шаг для тестов.
Объявление очередей и транзакции имеет смысл проверять интеграционными тестами с поднятыми RabbitMQ и PostgreSQL.
