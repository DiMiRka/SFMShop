# Масштабируемая архитектура для SFMShop

## Компоненты

### 1. Клиентский слой

* Web клиенты
* CDN (Cloudflare / AWS CloudFront) для статики (JS, CSS, изображения)

---

### 2. Балансировщик нагрузки

* **Nginx**
* Распределяет трафик между API инстансами

```id="arch1"
Client → CDN → Load Balancer → API Instances
```

---

### 3. API слой

* FastAPI приложения (несколько экземпляров)
* Stateless
* Запуск через Uvicorn

```id="arch2"
[API-1, API-2, API-3, ..., API-N]
```

Функции:

* обработка HTTP-запросов
* валидация
* orchestration логики

---

### 4. Кэш (Redis)

* хранение часто запрашиваемых данных
* rate limiting
* временные данные

```id="arch3"
API → Redis → (cache hit) → response
API → DB → Redis → response
```

---

### 5. База данных

#### PostgreSQL Cluster

* **Primary (write)**
* **Replica (read)**

```id="arch4"
Write → Primary DB
Read  → Replica DB (1..N)
```

---

### 6. Очереди сообщений

* **RabbitMQ**

Используется для:

* асинхронных задач (email, отчёты)
* обработки платежей

```id="arch5"
API → RabbitMQ → Worker
```

---

### 7. Background Workers

* Celery
* обработка задач из очереди

---

## Масштабирование

### Горизонтальное масштабирование API

* добавление новых инстансов
* auto-scaling (Kubernetes HPA)

```id="scale1"
CPU > 70% → +1 instance
CPU < 30% → -1 instance
```

---

### Масштабирование базы данных

#### Горизонтальное масштабирование

* добавление read-replicas

#### Вертикальное масштабирование

* увеличение CPU/RAM для primary

---

## Стратегия кэширования

### Процесс

```id="cache1"
1. Проверка Redis
2. Нет → запрос в БД
3. Сохранение в Redis
```

---

### Что кэшируется

* продукты
* списки товаров
* пользователи
* заказы (частично)

---

### TTL стратегия

* продукты: 10–15 мин
* пользователи: 5–10 мин
* горячие данные: 1–5 мин

---

### Инвалидация

* при изменении данных:

  * delete по ключу
  * delete по паттерну

---

## Обработка пиковых нагрузок

### 1. Autoscaling

* автоматическое увеличение API инстансов
* масштабирование Redis и workers

---

### 2. Rate Limiting

* ограничение запросов на пользователя/IP
* защита от перегрузки

---

### 3. Queue buffering

* RabbitMQ сглаживает пики
* задачи не теряются при перегрузке

---

### 4. Graceful degradation

* отключение вторичных функций:

  * рекомендации
  * аналитика

---

## Отказоустойчивость

### 1. Health Checks

* `/health` endpoint
* проверка:

  * DB
  * Redis
  * очередь

---

### 2. Автоматическое восстановление

* Kubernetes:

  * restart контейнеров
  * пересоздание pod'ов

---

### 3. Репликация

* PostgreSQL replicas
* Redis replication

---

### 4. Резервное копирование

* ежедневные backup БД
* хранение в S3 / object storage

---

### 5. Circuit Breaker

* защита от падения зависимостей
* fallback логика

---

## Мониторинг и алертинг

### Метрики

* Prometheus
* Grafana

---

### Логи

* централизованное логирование (ELK stack)

---

### Алерты

* CPU > 80%
* latency > threshold
* ошибки 5xx

---

## Метрики и SLA

### Целевые показатели

* **RPS:** 5000+

* **Latency:**

  * p50 < 50 ms
  * p95 < 150 ms
  * p99 < 300 ms

* **Availability:** 99.9%+

---

### SLA

* uptime: 99.9%
* max downtime: ~43 мин/месяц

---

## План масштабирования

### До 1000 RPS

* 2 API инстанса
* 1 DB
* Redis

---

### До 5000 RPS

* 5–10 API инстансов
* PostgreSQL + replicas
* Redis cluster
* RabbitMQ

---

### 5000+ RPS

* Kubernetes
* auto-scaling
* DB sharding
* CDN
* распределённые очереди

---

## Итог

Архитектура SFMShop:

* масштабируется горизонтально
* использует кэш и очереди
* разделяет read/write нагрузки
* устойчива к сбоям
* готова к высоким нагрузкам (5000+ RPS)

Это обеспечивает стабильную работу системы при росте пользователей и пиковых нагрузках
