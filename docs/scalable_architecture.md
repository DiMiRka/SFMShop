# Масштабируемая архитектура SFMShop

Документ описывает, как SFMShop должен выдерживать рост нагрузки до 5000+ RPS\
Это целевая схема: в каждом разделе отмечено, что уже есть в проекте\
Общий дизайн в [system_design.md](system_design.md), расчёт текущей нагрузки в [hosting_strategy.md](hosting_strategy.md)

## Компоненты

```text
Client → CDN → Load Balancer → [API-1, API-2, ..., API-N] → Redis / PostgreSQL / RabbitMQ
```

### Клиентский слой

- веб-клиенты
- CDN (Cloudflare, AWS CloudFront) для статики: JS, CSS, изображения

В проекте нет фронтенда и статики, CDN понадобится вместе с ними

### Балансировщик нагрузки

Распределяет трафик между инстансами API\
В Kubernetes это Service типа `LoadBalancer`, на VM это Nginx

### API

- несколько экземпляров FastAPI под Uvicorn
- stateless: состояние только в PostgreSQL и Redis
- обработка HTTP-запросов, валидация, бизнес-логика в сервисах

### Кэш (Redis)

```text
API → Redis → (hit) → ответ
API → Redis → (miss) → PostgreSQL → Redis → ответ
```

Хранит часто запрашиваемые данные: каталог, пользователей, заказы\
Rate limit сейчас хранится в памяти процесса, при нескольких инстансах его нужно перенести в Redis

### База данных

```text
Write → Primary
Read  → Replica (1..N)
```

В коде запись и чтение уже разделены на две сессии, реплики добавляются без изменения кода

### Очередь сообщений (RabbitMQ)

```text
Service → exchange → очередь → Consumer
```

Сейчас через RabbitMQ идут события для инвалидации кэша и уведомлений о заказах\
Позже через неё же пойдут email, отчёты и платежи\
Подробно в [message_queue_architecture.md](message_queue_architecture.md)

### Фоновые обработчики

Сейчас консьюмер работает внутри процесса API\
При росте нагрузки его выносят в отдельный deployment и масштабируют независимо от API

## Масштабирование

### API

Kubernetes HPA добавляет и убирает поды по загрузке CPU\
В `deploy/k8s/hpa.yaml`: от 1 до 5 подов, целевая загрузка CPU 60%

### База данных

- горизонтально: больше read-реплик
- вертикально: больше CPU и RAM для primary

## Кэширование

### Процесс

```text
1. Проверка Redis
2. Промах → запрос в БД
3. Запись результата в Redis
```

### Что кэшируется

- товары и списки товаров
- пользователи
- заказы

### TTL

Сейчас у всех ключей TTL 15 минут\
Целевая схема:

- товары: 10–15 минут
- пользователи: 5–10 минут
- горячие данные: 1–5 минут

### Инвалидация

При изменении данных ключи удаляются по имени и по паттерну, событие приходит через RabbitMQ

## Пиковые нагрузки

- **Autoscaling:** HPA добавляет поды API, отдельно масштабируются Redis и консьюмеры
- **Rate limiting:** ограничение запросов на пользователя или IP.\
  Сейчас лимиты стоят на вход и на ИИ-ассистента
- **Буфер в очереди:** RabbitMQ сглаживает пики, задачи не теряются при перегрузке консьюмера
- **Graceful degradation:** при перегрузке отключаются вторичные функции, например рекомендации и аналитика.\
  ИИ-ассистент уже работает так: если провайдер недоступен, эндпоинт отвечает 503, остальной API работает

## Отказоустойчивость

| Механизм | Что делает | В проекте |
| --- | --- | --- |
| Health checks | эндпоинт `/health` проверяет БД, Redis и очередь, Kubernetes перезапускает под | нет |
| Автовосстановление | Kubernetes перезапускает контейнеры и пересоздаёт поды | есть через Deployment |
| Репликация | реплики PostgreSQL и Redis | реплика PostgreSQL поддержана в коде |
| Резервное копирование | ежедневный backup БД в S3 или object storage | нет |
| Повторы и деградация | повтор с задержкой, запасной сценарий при отказе зависимости | есть для RabbitMQ, курсов валют и LLM |

Публикация события в RabbitMQ не ломает уже выполненную операцию: заказ создаётся, даже если брокер недоступен

## Мониторинг и алертинг

- метрики: Prometheus и Grafana
- логи: централизованное хранилище (ELK).\
  Сейчас Loguru пишет в stdout и файлы, ошибки уходят в Sentry
- алерты: CPU > 80%, latency выше порога, рост ошибок 5xx

## Целевые показатели

- RPS: 5000+
- latency: p50 < 50 ms, p95 < 150 ms, p99 < 300 ms
- доступность 99.9%: не больше ~43 минут простоя в месяц

## План масштабирования

| Нагрузка | Что нужно |
| --- | --- |
| до 1000 RPS | 2 инстанса API, одна БД, Redis |
| до 5000 RPS | 5–10 инстансов API, PostgreSQL с репликами, Redis cluster, RabbitMQ |
| 5000+ RPS | Kubernetes с autoscaling, шардирование БД, CDN, распределённые очереди |

## Итог

Архитектура масштабируется горизонтально, разделяет чтение и запись, снижает нагрузку кэшем и очередями
и переживает отказ вторичных зависимостей\
Чтобы дойти до целевых 5000+ RPS, не хватает health checks, метрик, общего хранилища rate limit и отдельного деплоя консьюмеров
