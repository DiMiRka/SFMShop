# Системный дизайн проекта SFMShop

## Архитектура

### Компоненты:

* **API сервис (FastAPI)** — обработка HTTP-запросов (users, products, orders)
* **PostgreSQL Primary** — основная база данных (запись)
* **PostgreSQL Replica** — реплика для чтения
* **Redis** — кэширование и временные данные
* **Nginx** — балансировщик нагрузки
* **Uvicorn/Gunicorn** — запуск приложения
* **Docker / Docker Compose** — контейнеризация
* **(опционально) Celery / Background workers** — асинхронные задачи

---

## Масштабирование

### Горизонтальное масштабирование API

Приложение масштабируется за счёт запуска нескольких экземпляров:

```id="e7d8sf"
Client → Nginx → [App Instance 1, App Instance 2, App Instance N]
```

* каждый инстанс — stateless
* состояние хранится в Redis / БД
* масштабирование через Docker / Kubernetes

---

### Масштабирование базы данных

#### Primary / Replica

```id="tqz1lw"
Write → Primary DB
Read  → Replica DB
```

* все записи идут в primary
* чтение (GET-запросы) — в реплику
* снижает нагрузку на основную БД

---

### Вертикальное масштабирование

* увеличение CPU / RAM для:

  * PostgreSQL
  * Redis

---

## Кэширование

### Использование Redis

Кэш применяется для:

* списка товаров (`products:{limit}:{offset}`)
* конкретного товара (`product:{id}`)
* пользователей (`user:{id}`)
* заказов (`order:{id}`)

---

### Стратегия кэширования

* **Cache Aside (Lazy Loading)**:

  1. проверка кэша
  2. при отсутствии → запрос в БД
  3. запись в кэш

---

### Инвалидация кэша

* при изменении данных:

  * delete по ключу
  * delete по паттерну (`products:*`)
* используется batch удаление

---

### TTL (Time To Live)

* стандартный TTL: 10–15 минут
* для часто меняющихся данных — меньше

---

## Балансировка нагрузки

### Nginx

```id="2zk9dp"
upstream backend {
    server app1:8000;
    server app2:8000;
    server app3:8000;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

---

### Алгоритмы балансировки

* round-robin (по умолчанию)
* least connections (опционально)

---

## Работа с соединениями

* использование connection pool:

  * PostgreSQL (asyncpg)
  * Redis
* повторное использование http-клиентов (httpx)

## Метрики производительности

### Целевые показатели

* **RPS (requests per second):**

  * старт: 500–1000 RPS
  * цель: 3000+ RPS

* **Latency:**

  * p50: < 50 ms
  * p95: < 150 ms
  * p99: < 300 ms

---

### Узкие места

* база данных (основное)
* сетевые вызовы
* отсутствие кэша

---

## Стратегия масштабирования

### Этап 1 (до 1000 RPS)

* 1–2 инстанса API
* 1 PostgreSQL
* Redis

---

### Этап 2 (до 3000 RPS)

* 3–5 инстансов API
* PostgreSQL + Replica
* агрессивное кэширование

---

### Этап 3 (5000+ RPS)

* Kubernetes
* autoscaling (HPA)
* шардирование БД (при необходимости)
* CDN для статических данных

## Итог

Система SFMShop:

* масштабируется горизонтально
* использует кэш для снижения нагрузки
* применяет репликацию БД
* балансирует нагрузку через Nginx

Это позволяет выдерживать высокую нагрузку и обеспечивает отказоустойчивость.
