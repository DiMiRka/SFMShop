# Микросервис оплаты payment-service

payment-service лежит в папке `payment_service/` рядом с основным сервисом и владеет деньгами пользователей: кошельками,
журналом операций и платежами\
Основной сервис хранит только заказы и обращается к payment-service по HTTP через `sfmshop/clients/payment_client.py`

## Ответственность

payment-service отвечает за:

- кошельки пользователей и их балансы
- журнал операций: пополнения, списания и возвраты
- платежи за заказы и их статусы: `success`, `failed`, `refunded`
- идемпотентность: повтор запроса не списывает и не зачисляет деньги второй раз

payment-service не отвечает за пользователей, заказы и товары: он знает только их id

## Почему деньги живут здесь

Если бы баланс остался в основном сервисе, payment-service должен был бы вызывать его обратно (`POST /users/{id}/withdraw`)\
Получился бы круг «магазин → оплата → магазин», а каждый из двух сетевых вызовов требовал бы своей идемпотентности\
Когда кошелёк и платёж лежат в одной базе, проверка баланса, списание и запись платежа идут одной транзакцией

## Структура

Слои те же, что в основном сервисе, пакет называется `payment`, чтобы не пересекаться с `sfmshop` при импорте:

```text
payment_service/

│   ├── api/                 # payments.py, wallets.py, health.py, зависимости

├── alembic/
├── tests/
├── Dockerfile

```

## Модель данных

```text
wallets:              user_id (PK), balance >= 0, updated_at
payments:             id, order_id, user_id, amount > 0, status, idempotency_key (уникальный), detail, created_at
wallet_transactions:  id, user_id, amount (+ пополнение и возврат, − списание), kind, payment_id, idempotency_key, created_at
```

- **Частичный уникальный индекс `uq_payments_order_success`**\
  Успешный платёж по заказу может быть только один (`UNIQUE (order_id) WHERE status = 'success'`)\
  Неудачных попыток может быть сколько угодно, поэтому после `failed` заказ можно оплатить снова
- **Журнал операций**\
  Каждое изменение баланса оставляет строку в `wallet_transactions`, сумма строк равна балансу\
  По журналу видно, откуда взялись деньги, и баланс можно пересчитать
- **`CHECK (balance >= 0)`**\
  Даже ошибка в коде не уведёт баланс в минус (база отклонит такую запись)

## Эндпоинты

Все пути под `/api/v1` требуют заголовок `X-Service-Token` с общим секретом `PAYMENT_SERVICE_TOKEN`\
Если токен не задан в настройках, сервис отклоняет все запросы, а не пускает всех\
Проверки `/health/live` и `/health/ready` доступны без токена

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/v1/payments` | списать деньги за заказ, нужен заголовок `Idempotency-Key` |
| GET | `/api/v1/payments/{id}` | платёж целиком |
| POST | `/api/v1/payments/{id}/refund` | вернуть деньги за успешный платёж |
| GET | `/api/v1/wallets/{user_id}` | баланс, для неизвестного пользователя `0.00` |
| POST | `/api/v1/wallets/{user_id}/top-up` | пополнить баланс, нужен заголовок `Idempotency-Key` |

### Оплата

Запрос:

```json
{"order_id": 1, "user_id": 10, "amount": "150.50"}
```

| Ситуация | Код | Тело |
| --- | --- | --- |
| деньги списаны | 201 | `{"id": 100, "order_id": 1, "status": "success"}` |
| повтор с тем же ключом или заказ уже оплачен | 200 | тот же платёж, без нового списания |
| не хватает денег | 409 | `{"id": 101, "order_id": 1, "status": "failed", "detail": "Недостаточно средств"}` |
| ключ уже использован с другой суммой, заказом или пользователем | 422 | `{"detail": "..."}` |

Логика внутри одной транзакции:

1. заблокировать кошелёк пользователя (`SELECT ... FOR UPDATE`, кошелёк создаётся при первом обращении)
2. если платёж с этим ключом уже есть, вернуть его
3. если у заказа уже есть успешный платёж, вернуть его
4. списать деньги и записать операцию или сохранить платёж со статусом `failed`

Блокировка кошелька выстраивает параллельные оплаты одного пользователя в очередь\
Поэтому два одновременных запроса не спишут деньги дважды за один заказ и не уведут баланс в минус,
а частичный индекс страхует это правило на уровне базы

### Возврат

Возврат успешного платежа зачисляет деньги обратно и переводит платёж в `refunded`\
Повторный возврат того же платежа ничего не меняет и возвращает его же, возврат неуспешного платежа даёт 409

### Пополнение

Повтор с тем же `Idempotency-Key` не зачисляет деньги второй раз\
Двойной клик администратора по кнопке пополнения не удвоит баланс

## Взаимодействие сервисов

```text
Order Service ──POST /api/v1/payments──→ Payment Service ──→ payment_db
      ↑                                        │
      └──────────────── ответ ─────────────────┘
```

1. Order Service создаёт заказ со статусом `pending` (статусы и переходы в `sfmshop/core/order_status.py`)
2. Order Service вызывает `POST /api/v1/payments` через `PaymentClient.charge`
3. по ответу Order Service переводит заказ в `paid` или `failed` и запоминает `orders.payment_id`,
   при недоступности сервиса заказ остаётся в `pending`, а `POST /v1/orders/` всё равно отвечает 201
4. при удалении оплаченного заказа Order Service вызывает `POST /api/v1/payments/{id}/refund`
5. баланс и пополнение (`/v1/users/{id}/balance`, `/v1/users/{id}/top-up`) проксируются в `/api/v1/wallets`

### Сетевой вызов вне транзакции

`OrderService.pay_order` не держит блокировку заказа, пока ждёт payment-service:

1. транзакция 1 - заблокировать заказ, проверить, что его можно оплатить, запомнить сумму и покупателя
2. вызов payment-service без открытой транзакции
3. транзакция 2 - снова заблокировать заказ и записать результат

Между шагами заказ может измениться, поэтому шаг 3 проверяет его заново:

- **Параллельный запрос уже записал этот же платёж**\
  Возвращается заказ как есть, без второго события `order.paid`
- **Заказ отменили или удалили, пока шла оплата**\
  Деньги возвращаются через `refund`, клиент получает 409 «Заказ изменился во время оплаты»

Удаление оплаченного заказа устроено так же (сначала возврат денег вне транзакции,
затем удаление, которое отменяется с 409, если статус заказа успел измениться)\
Повторный возврат безопасен (payment-service возвращает деньги за платёж только один раз)

## Развёртывание

- payment-service на порту 8001, основной сервис на 8000
- своя база `payment_db` в отдельном контейнере `payment-db` (сервис не читает чужие таблицы и масштабируется отдельно)
- при старте контейнер применяет миграции (`alembic upgrade head`), затем запускает uvicorn
- в Docker Compose порт 8001 наружу не публикуется (сервис доступен только основному приложению внутри сети compose,
  `app` стартует после того, как payment-service прошёл проверку `/health/ready`)

Настройки payment-service:

```text
PAYMENT_DB_HOST, PAYMENT_DB_PORT, PAYMENT_DB_NAME, PAYMENT_DB_USER, PAYMENT_DB_PASSWORD
PAYMENT_SERVICE_TOKEN
```

В основном сервисе:

```text
PAYMENT_SERVICE_URL=http://payment:8001
PAYMENT_SERVICE_TOKEN=тот же секрет, что у payment-service
```

Без `PAYMENT_SERVICE_URL` клиент не создаётся (заказы остаются в `pending`, баланс и пополнение отвечают 503)\
Остальные настройки: `PAYMENT_TIMEOUT` (ожидание ответа 5 с), `PAYMENT_CONNECT_TIMEOUT` (подключение 2 с),
`PAYMENT_MAX_RETRIES` (повторы 3)

## Надёжность клиента

- **Один HTTP-клиент на приложение**\
  `httpx.AsyncClient` создаётся в lifespan и закрывается при остановке, соединения переиспользуются между запросами
- **Повторы с экспоненциальной задержкой**\
  На сетевые ошибки, таймауты и ответы 429, 500, 502, 503, 504: пауза 0.5 с, 1 с, 2 с, не больше 5 с\
  Ответ 409 это отказ в оплате, а не сбой, он не повторяется\
  Остальные 4xx означают ошибку в контракте и не повторяются
- **Ключ идемпотентности**\
  Каждый вызов `charge` получает новый заголовок `Idempotency-Key`, и все повторы внутри вызова идут с ним\
  Если ответ потерялся по таймауту уже после списания, повтор с тем же ключом вернёт сохранённый результат, а не спишет деньги второй раз\
  Новая попытка оплаты (`POST /v1/orders/{id}/pay` после `failed`) получает новый ключ
- **Недоступность сервиса**\
  После всех повторов клиент бросает `PaymentUnavailableError` (503), заказ остаётся в `pending`, оплату можно повторить позже
- **Метрика**\
  `sfmshop_payment_requests_total` с меткой `result`: `success`, `failed`, `unavailable`
- асинхронный вариант: Order Service публикует `order.created`, payment-service забирает событие из RabbitMQ.\
  Так основной сервис не ждёт ответа, но клиенту нужно узнавать статус оплаты отдельно

## Тесты

Тесты payment-service идут на настоящем PostgreSQL: блокировки, частичный индекс и `CHECK` на фейках не проверить\
Перед запуском тесты сами создают базу `payment_test`, применяют миграции и очищают таблицы перед каждым тестом

```bash
cd payment_service
pytest --cov=payment
```

Адрес базы берётся из `PAYMENT_DB_*`\
Проверяются: списание и запись в журнал, отказ без изменения баланса, повтор с тем же ключом, ключ с другими параметрами,
повторная оплата оплаченного заказа, оплата после `failed`, пять одновременных оплат одного заказа (списание одно),
одновременные оплаты разных заказов (баланс не уходит в минус), возврат один раз, пополнение по ключу,
ограничения базы, совпадение миграций с моделями и откат миграций, коды ответов API, сервисный токен на каждом маршруте

## Итог

payment-service изолирован, имеет свою БД, общается с другими сервисами по HTTP
и не содержит логики других доменов\
Это позволяет масштабировать и развёртывать оплату независимо от остального магазина
