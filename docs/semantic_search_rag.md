# Семантический поиск и RAG

`GET /v1/products/semantic-search` ищет товары по смыслу запроса и по названию одновременно \
ИИ-ассистент получает найденные товары через инструмент `semantic_search_products` и отвечает только по ним (это и есть RAG)

## Устройство

```
sfmshop/clients/embeddings/base.py             # Protocol EmbeddingClient
sfmshop/clients/embeddings/openai.py           # OpenAI embeddings: пачки, повторы SDK, метрики токенов и расходов
sfmshop/clients/embeddings/__init__.py         # реестр провайдеров, выбор по EMBEDDING_PROVIDER
sfmshop/services/product_index_service.py      # ProductIndexer: текст товара → вектор → product_embeddings
sfmshop/services/queue_consumer.py             # очередь embedding_queue на product.created и product.updated
sfmshop/services/product_search_service.py     # гибридный поиск и объединение результатов через RRF
sfmshop/repositories/product_repository.py     # semantic_search: косинусное расстояние, порог, фильтры
scripts/reindex_products.py                    # переиндексация всех товаров
```

## Как это работает

**Индексация**
1. Админ создаёт или меняет товар, после коммита уходит событие `product.created` или `product.updated`
2. Консьюмер `embedding_queue` берёт текст товара (название и описание) и считает хэш текста вместе с моделью
3. Если хэш совпадает с сохранённым, вектор актуален и API не вызывается
4. Иначе текст уходит в OpenAI, вектор записывается в `product_embeddings` через `INSERT ... ON CONFLICT DO UPDATE`

**Поиск**
1. Запрос превращается в вектор (вектор кэшируется в Redis на сутки)
2. pgvector находит ближайшие товары по косинусному расстоянию с порогом похожести
3. Параллельно работает обычный поиск по названию на `pg_trgm`
4. Два списка объединяются через RRF

## Почему pgvector, а не отдельная векторная БД

- **Одна система вместо двух**\
  Товары и векторы лежат в одной базе: JOIN, фильтры по цене и наличию в том же запросе, общие транзакции и бэкапы
- **Масштаб**\
  Каталог на тысячи или десятки тысяч товаров pgvector обслуживает без проблем\
  Qdrant или Pinecone имеют смысл при десятках миллионов векторов или когда нужен отдельный кластер под поиск

**Цена решения:** нагрузка поиска ложится на ту же PostgreSQL (читаем с реплики как и остальной каталог)

## Почему отдельная таблица

Векторы хранятся в `product_embeddings` (`product_id`, `embedding vector(1536)`, `model`, `content_hash`, `updated_at`), а не колонкой в `products`

- **Видно чем посчитан вектор**\
  Векторы разных моделей несравнимы, `model` и хэш позволяют понять, что вектор устарел
- **Обновления товара не трогают вектор**\
  Смена цены или остатка не переписывает строку с вектором
- **Удаление товара** убирает вектор через `ON DELETE CASCADE`, отдельное событие не нужно

## Почему HNSW, а не IVFFlat

Индекс `ix_product_embeddings_embedding_hnsw` с `vector_cosine_ops`

- **HNSW** (граф соседей в несколько слоёв)\
  Работает сразу, в том числе на пустой таблице, не требует обучения и хорошо держит баланс скорости и точности
- **IVFFlat** (векторы делятся на кластеры)\
  Строится быстрее и занимает меньше места, но индекс нужно строить на уже заполненной таблице,
  а при росте данных перестраивать, иначе точность падает

Оба индекса приблизительные (ANN): изредка могут пропустить лучшего соседа в обмен на скорость

## Почему индексация через очередь

- Вызов OpenAI занимает сотни миллисекунд и может упасть, админ не должен ждать его при сохранении товара
- Если API недоступен, сообщение повторяется через `embedding_queue.retry`, после исчерпания попыток уходит в `embedding_queue.error`
- API вызывается вне транзакции: соединение из пула не держится открытым, пока ждём ответа
- Запись идёт в новой транзакции с `FOR KEY SHARE` на товары: товар не удалят, пока пишется его вектор,
  а уже удалённый товар просто пропускается

`python -m scripts.reindex_products` проходит по всем товарам пачками и пропускает неизменившиеся\
`--force` пересчитывает всё, это нужно после смены модели

## Гибридный поиск и RRF

- **Векторы** понимают смысл: «подарок бегуну» находит «наушники для бега», хотя общих слов нет
- **Триграммы** точны на названиях, артикулах и опечатках: «RTX 4070» или «мыш беспроводня»

Оценки двух поисков несравнимы (косинусная похожесть и `word_similarity`), поэтому они не складываются\
RRF смотрит только на места в списках: товар получает `1 / (60 + место)` за каждый список\
Товар, найденный обоими способами, оказывается наверху, а константа 60 сглаживает разницу между первыми местами\
В ответе у товара есть `similarity` (близость по смыслу от 0 до 1) и `matched_by` (`semantic`, `text` или оба)

## Порог похожести

`SEMANTIC_MIN_SIMILARITY=0.3` отсекает товары, которые ближайшие, но не похожи (ближайший сосед есть всегда)\
Значение стартовое: его подбирают на реальных запросах, смотря где начинается мусор

## Фильтры и iterative scan

Цена и наличие это точные условия, поэтому они в `WHERE`, а не в векторе\
HNSW по умолчанию берёт около 40 кандидатов и только потом применяет фильтр\
Если большинство кандидатов отсеется, результатов будет меньше `limit`\
С pgvector 0.8 запрос выполняется с `SET LOCAL hnsw.iterative_scan = strict_order`: индекс продолжает поиск,
пока не наберёт нужное количество, а порядок по расстоянию сохраняется

## RAG в ассистенте

Инструмент `semantic_search_products` отдаёт модели id, название, описание, цену, остаток и `similarity`\
Системный промпт велит искать через него, когда покупатель описывает задачу, и советовать только из найденного

Защита та же, что у остальных инструментов:
- товары, которых не было в результатах инструментов, отбрасываются из `product_ids`
- аргументы проверяются Pydantic (`query` от 2 до 200 символов, `limit` до 10, `min_price` не больше `max_price`)
- описание товара пишет только администратор, поэтому текст в контексте модели не приходит от покупателей

## Расходы и метрики

- `sfmshop_embedding_tokens_total` и `sfmshop_embedding_cost_usd_total` по модели\
  Стоимость оценивается по `EMBEDDING_USD_PER_MILLION_TOKENS` (у `text-embedding-3-small` $0.02 за 1M токенов)
- `sfmshop_embedding_requests_total`: `ok` и `unavailable`
- `sfmshop_products_indexed_total`: `indexed`, `unchanged`, `missing`
- `sfmshop_semantic_searches_total`: `hybrid`, `text` (эмбеддинги выключены), `fallback` (API недоступен)

Чтобы не платить за каждый запрос:
- вектор запроса кэшируется в Redis (`EMBEDDING_QUERY_CACHE_TTL`)
- у эндпоинта rate limit по IP (`RATE_LIMIT_SEMANTIC_SEARCH`)
- товары пересчитываются только при изменении текста

## Устойчивость

- Без `OPENAI_API_KEY` эмбеддинги выключены, приложение стартует, поиск работает по названию (`mode: "text"`)
- Если API эмбеддингов недоступен, поиск тоже переходит на название, а не отвечает 503
- Таймаут и повторы с экспоненциальной задержкой берутся из SDK (`EMBEDDING_TIMEOUT`, `EMBEDDING_MAX_RETRIES`)
- `EMBEDDING_DIMENSIONS` должна совпадать с колонкой `vector(1536)`, иначе приложение не стартует

## Возможное развитие

- Вынести поиск на отдельную реплику, если он начнёт мешать каталогу
- Подбирать порог и константу RRF на размеченном наборе запросов (метрики качества: recall@k, MRR)
- Индексировать отзывы и характеристики товаров отдельными чанками
- Перейти на `halfvec` (половинная точность), если индекс станет большим: вдвое меньше памяти почти без потери качества
