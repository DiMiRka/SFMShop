# Стратегия хостинга для проекта SFMShop

## Оценка нагрузки

В SFMShop основная нагрузка распределяется между API группами auth, products, orders, users

Цифры взяты из учебного расчета в scripts/hosting_capacity_demo.py\
В скрипте для каждого эндпоинта заданы ожидаемая нагрузка в RPS и среднее время ответа в миллисекундах\
Расчет использует запас 1.5x

| Тип нагрузки | RPS | Обоснование |
| --- | ---: | --- |
| Текущая нагрузка | 70 RPS | Стартовый этап проекта: мало пользователей, основной трафик идет на каталог товаров и чтение данных |
| Ожидаемая нагрузка | 227 RPS | Сумма ожидаемой нагрузки по текущим эндпоинтам SFMShop из scripts/hosting_capacity_demo.py |
| Пиковая нагрузка | 341 RPS | Ожидаемая нагрузка 227 RPS с запасом 1.5x: 227 * 1.5 = 340.5 |

По расчету получается:

- суммарная ожидаемая нагрузка: 227 RPS
- запас на пики: 1.5x
- расчетная пиковая нагрузка: 341 RPS
- общее число воркеров с запасом: 38

ИИ-ассистент (`POST /v1/assistant`) в расчет не входит: его ограничивает не сервер, а задержка и стоимость запросов к LLM\
Нагрузку на него держит rate limit `RATE_LIMIT_ASSISTANT` (по умолчанию 10 запросов в минуту)

Самая большая нагрузка ожидается на чтение товаров:

- products_list: 60 RPS
- products_get: 45 RPS
- orders_get: 20 RPS
- users_get: 18 RPS

## Выбор хостинга

| Нагрузка | Рекомендуемый хостинг |
| --- | --- |
| Меньше 100 RPS | VPS или PaaS |
| 100-1000 RPS | Cloud |
| Больше 1000 RPS | Cloud + Kubernetes |

Для SFMShop выбран вариант: Cloud (AWS или Google Cloud)

Почему выбран Cloud:

- ожидаемая нагрузка 227 RPS попадает в диапазон 100-1000 RPS
- пиковая нагрузка 341 RPS тоже остается в диапазоне Cloud
- в проекте есть PostgreSQL, Redis, MongoDB и RabbitMQ, их удобно выносить в managed сервисы
- в проекте уже есть Dockerfile, Docker Compose, Kubernetes Deployment, Service, HPA и Secrets
- Cloud оставляет запас для роста без срочного переезда на другую платформу

Почему не VPS как основной вариант:

- VPS подходит для текущей нагрузки около 70 RPS, но для 227-341 RPS нужно более удобное масштабирование
- отказоустойчивость, бэкапы, мониторинг и балансировку придется настраивать вручную
- при росте трафика добавлять ресурсы медленнее

Почему не PaaS как основной вариант:

- PaaS удобен для демо и MVP, но SFMShop использует несколько зависимостей: PostgreSQL, Redis, MongoDB, RabbitMQ
- при росте нагрузки и числа сервисов PaaS может стать дорогим и менее гибким
- меньше контроля над сетями, очередями, масштабированием и инфраструктурой

## Стратегия масштабирования

### Этап 1: текущая нагрузка до 100 RPS

На старте достаточно одного небольшого cloud инстанса или минимального managed container setup

Минимальный набор:

- 1-2 экземпляра API
- небольшой managed PostgreSQL
- Redis для кэша
- базовый мониторинг
- ручное масштабирование при необходимости

### Этап 2: ожидаемая нагрузка около 227 RPS

На этом этапе нужен Cloud с возможностью горизонтального масштабирования

Что нужно:

- несколько реплик API
- Load Balancer перед приложением
- Redis кэш для частых запросов каталога
- managed PostgreSQL и managed Redis
- RabbitMQ для асинхронных событий
- requests/limits ресурсов для контейнеров
- HPA для масштабирования по CPU или RPS

### Этап 3: пиковая нагрузка около 341 RPS

Пиковая нагрузка покрывается запасом 1.5x, который заложен в расчет воркеров

Нужно контролировать:

- количество активных pod API
- время ответа products_list, products_get, orders_get
- нагрузку на PostgreSQL
- hit rate кэша Redis
- длину очередей RabbitMQ
- процент ошибок 4xx/5xx
- p95/p99 latency

### Этап 4: рост выше 1000 RPS

Если нагрузка превысит 1000 RPS, стратегия меняется на Cloud + Kubernetes

Что добавить:

- горизонтальное масштабирование API через Kubernetes HPA
- разделение API и worker процессов
- read replica для PostgreSQL (разделение чтения и записи в коде уже есть)
- более агрессивное кэширование каталога товаров
- CDN для статических файлов
- отдельное масштабирование RabbitMQ consumers
- централизованные логи и алерты
- нагрузочное тестирование перед релизами

## Мониторинг

Минимальные метрики:

- RPS по каждому эндпоинту
- среднее время ответа
- p95 и p99 latency
- CPU и RAM контейнеров
- количество pod API
- ошибки 5xx
- количество подключений к PostgreSQL
- Redis hit/miss ratio
- длина очередей RabbitMQ

Алерты:

- 5xx error rate выше порога
- p95 latency выше целевого значения
- CPU стабильно выше 70-80%
- PostgreSQL connections близко к лимиту
- RabbitMQ queue length растет и не снижается
- Redis недоступен

## Оптимизация

При росте нагрузки сначала оптимизируем самые частые и дорогие запросы:

- кэшировать products_list и products_get в Redis (уже сделано)
- добавлять индексы в PostgreSQL для частых фильтров и поиска
- выносить тяжелые операции в RabbitMQ workers
- уменьшать число запросов к базе данных на один API запрос
- использовать пагинацию для списков
- отдельно масштабировать API и фоновые обработчики

## Итог

Для SFMShop выбран хостинг Cloud (AWS или Google Cloud)

Выбор связан с нагрузкой:

- текущая нагрузка 70 RPS, ее выдержали бы VPS или PaaS
- ожидаемая нагрузка 227 RPS, это диапазон Cloud
- пиковая нагрузка 341 RPS, Cloud оставляет запас для роста
- при росте выше 1000 RPS стратегия меняется на Cloud + Kubernetes с горизонтальным масштабированием и managed сервисами
