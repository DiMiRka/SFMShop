# Подход к тестированию в проекте SFMShop

## Обзор

Тесты проверяют бизнес-логику, права доступа, API endpoints и связи между компонентами \
Ни один тест не обращается к реальным PostgreSQL, Redis, RabbitMQ, MongoDB, внешним HTTP API или LLM, поэтому весь набор
выполняется за несколько секунд локально и в CI без поднятой инфраструктуры

Запуск с отчётом о покрытии:

```powershell
.\.venv\Scripts\python.exe -m pytest --cov=src --cov-report=term-missing
```

Результат: 198 тестов пройдены, общее покрытие `src` 98%

## Принципы

- **Без внешних сервисов** \
  Репозитории, кэш, очередь и HTTP-клиенты заменяются моками или фейками,
  FastAPI-зависимости подменяются через `app.dependency_overrides`
- **Тест на баг сначала падает** \
  Каждый тест, добавленный вместе с исправлением, проверялся на старом коде:
  без исправления он должен падать. \
  Так тест действительно ловит регрессию, а не проходит всегда
- **Права доступа проверяются через HTTP** \
  Правила доступа тестируются запросами к реальным маршрутам, а не только вызовами функций.\
  Так проверяется и подключение зависимостей, и коды ответов

## Ключевые сценарии безопасности

Эти тесты защищают от уже найденных и исправленных уязвимостей:

- чужой заказ нельзя увидеть или удалить, при попытке не меняются ни баланс, ни склад, ни очередь событий
- заказ всегда оформляется на текущего пользователя, `user_id` из тела запроса игнорируется
- обычный пользователь не может менять товары, читать чужие профили и менять `balance`, `is_active`, `is_admin`
- свой пароль меняется только с верным `current_password`, в том числе для админа
- деактивированный пользователь не может войти, обновить токен или пользоваться уже выданным токеном
- при ошибке 500 клиент получает общее сообщение, а исключение с traceback попадает в лог
- ИИ-ассистент не показывает модели чужой заказ, даже если пользователь называет себя администратором
  id товаров и заказов, которых не было в результатах инструментов, из ответа отбрасываются

## Техники

### Фикстуры

Общие фикстуры в `tests/conftest.py`:

- `sample_product`, `sample_user`, `sample_order` для доменных моделей
- `log_messages` собирает сообщения loguru во время теста, чтобы проверять логирование без перехвата stdout

### Параметризация

Используется для расчётной логики и для матрицы прав доступа: один тест проверяет несколько маршрутов
или ролей

```python
@pytest.mark.parametrize("method, url, body", [
    ("post", "/v1/products/", PRODUCT),
    ("put", "/v1/products/1", {"quantity": 2}),
    ("delete", "/v1/products/1", None),
])
def test_only_admin_can_change_products(method, url, body):
    ...
```

### Моки и фейки

- `MagicMock` и `AsyncMock` для точечных проверок вызовов (`assert_awaited_once`, `assert_not_awaited`)
- фейковые репозитории в `test_services.py` хранят состояние в памяти: после вызова сервиса можно проверить,
  что именно изменилось у пользователя, товара или заказа
- `HttpClientFake` возвращает заранее заданную последовательность ответов и исключений, так проверяются
  повторы и переключение между провайдерами курсов валют
- `app.dependency_overrides` подменяет сервисы и текущего пользователя в API-тестах
- `ScriptedLLM` в `test_assistant_service.py` — фейковый LLM-клиент: возвращает заранее заданную последовательность
  ответов (вызов инструмента → финальный ответ) и запоминает каждый запрос. По сохранённым сообщениям проверяется,
  что именно сервер отдал модели в результатах инструментов. Сервисы товаров и заказов в этих тестах настоящие,
  поверх фейковых репозиториев, поэтому проверка прав выполняется реальным кодом
- клиент Anthropic тестируется на уровне HTTP: в SDK передаётся `httpx2.MockTransport`, так проверяются
  повторы самого SDK и тело запроса без сети и ключа

### Контракт событий

Тесты очереди не придумывают события вручную: событие берётся из реального вызова сервиса
(`update_user`, `create_order`, `delete_user`) через фейковую очередь и передаётся консьюмеру.\
Если отправитель и получатель разойдутся в ключах (`user_ids` против `user_id`), тест упадёт

`FakeMessage` в `test_queue.py` отдаёт настоящий `ProcessContext` из aio_pika, а его `ack` и `reject`
падают при повторном вызове, как в библиотеке. \
Так тесты ловят двойное подтверждение сообщения (пустой контекст на его месте эту ошибку пропускал)

Порядок «коммит, потом событие» проверяет `TransactionLog`: он одновременно играет роль сессии
(`begin()`) и очереди (`publish_event`) и записывает события в один список

### Негативные сценарии через side_effect

```python
order_rep.create.side_effect = RuntimeError("DB error")
```

Так проверяется, что при падении БД событие в очередь не отправляется

### Особенности

- В Starlette 1.0 `app.debug` обычный атрибут, а стек middleware кэшируется при первом запросе.\
  Тест ошибки 500 сбрасывает `app.middleware_stack`, чтобы результат не зависел от `DEBUG` в локальном `.env`
- Для проверки 500 используется `TestClient(app, raise_server_exceptions=False)`, иначе исключение
  пробрасывается в тест вместо ответа
