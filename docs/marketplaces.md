# Интеграция с маркетплейсами Ozon и Wildberries

Магазин выгружает остатки и цены на Ozon и Wildberries и забирает оттуда новые заказы \
Интеграция написана по официальной документации [Ozon Seller API](https://docs.ozon.ru/api/seller/)
и [WB API](https://dev.wildberries.ru/) \
На реальном кабинете продавца не запускалась (для этого нужен аккаунт продавца и ключи API)

## Устройство

```
sfmshop/clients/marketplaces/base.py           # Protocol MarketplaceClient и общие dataclass (остаток, цена, заказ)
sfmshop/clients/marketplaces/http.py           # повторы на 429 и 5xx, Retry-After, троттлинг запросов
sfmshop/clients/marketplaces/ozon.py           # Ozon Seller API
sfmshop/clients/marketplaces/wildberries.py    # WB API
sfmshop/clients/marketplaces/__init__.py       # реестр площадок (площадка включается если заданы её ключи)
sfmshop/services/marketplace_sync_service.py   # выгрузка остатков и цен, импорт заказов
sfmshop/services/marketplace_scheduler.py      # запуск по расписанию и advisory lock
sfmshop/api/v1/marketplaces.py                 # синхронизация и привязки товаров
```

Таблицы:
- `marketplace_listings`: связь товара магазина с товаром на площадке (`offer_id`, у WB ещё `nmID` и `chrtId`),
  последние отправленные остаток и цена, время синхронизации и последняя ошибка
- `marketplace_orders`: импортированные заказы, уникальный ключ `(marketplace, external_id)`

## Почему Protocol и реестр

Сервис синхронизации работает с интерфейсом `MarketplaceClient` (`update_stocks`, `update_prices`, `fetch_orders`)
и не знает какая площадка перед ним \
Wildberries добавлен второй реализацией и одной строкой в реестре, сервис при этом не менялся \
Так же устроены провайдеры LLM и эмбеддингов в проекте

- **Без ключей модуль выключен**\
  Приложение стартует, эндпоинт синхронизации отвечает 503
- **Площадки независимы**\
  Каждая синхронизируется в своём `try`: если упал Ozon (или в его клиенте баг), WB всё равно обновится,
  а ошибка попадёт в `last_error` и в метрику

## Эндпоинты площадок

| | Ozon | Wildberries |
|---|---|---|
| Остатки | `POST /v2/products/stocks` | `PUT /api/v3/stocks/{warehouseId}` |
| Цены | `POST /v1/product/import/prices` | `POST /api/v2/upload/task` |
| Заказы | `POST /v4/posting/fbs/list` | `GET /api/v3/orders` и `POST /api/v3/orders/status` |
| Авторизация | `Client-Id` и `Api-Key` | токен в `Authorization` |
| Ожидание при 429 | `Retry-After` | `X-Ratelimit-Retry` |

У WB цены и остатки на разных хостах (`discounts-prices-api` и `marketplace-api`)

## Батчи и лимиты

| | Ozon | Wildberries |
|---|---|---|
| Остатки | 100 позиций в запросе, 80 запросов в минуту | 1000 позиций, 300 запросов в минуту |
| Цены | 1000 товаров, цену одного товара не чаще 10 раз в час | 1000 товаров, 10 запросов за 6 секунд |
| Заказы | страница до 100 | страница до 1000, период не больше 30 дней |

- **Батчи**\
  Список длиннее лимита режется на пачки (250 остатков Ozon уходят тремя запросами 100, 100, 50)
- **Троттлинг**\
  Между запросами к одному методу выдерживается интервал из документации (у остатков Ozon 0.75 секунды),
  поэтому до 429 обычно не доходит
- **Повторы**\
  429, 5xx, таймаут и обрыв соединения повторяются с экспоненциальной задержкой, а если площадка прислала
  `Retry-After` или `X-Ratelimit-Retry`, ждём столько сколько она сказала \
  Остальные 4xx не повторяются (запрос неправильный и повтор ничего не изменит)
- **Только изменения**\
  В `marketplace_listings` хранятся последние успешно отправленные остаток и цена, площадке уходит только разница \
  Иначе синхронизация раз в 5 минут обновляла бы цену 12 раз в час и упиралась бы в лимит Ozon \
  `POST /v1/marketplaces/sync?force=true` отправляет всё

## Ошибки внутри успешного ответа

- **Ozon**\
  Ответ HTTP 200, но в `result[].errors` по каждому товару может быть своя ошибка
  (например `TOO_MANY_REQUESTS` если остаток этой пары товар-склад обновляли меньше 30 секунд назад) \
  Результат разбирается по каждому `offer_id` (обновлённые получают новые `synced_*`, остальные `last_error` и уйдут в следующий раз)
- **WB цены**\
  Если цены уже такие же как в запросе, то WB отвечает HTTP 400 с текстом «already set» \
  Для синхронизации это не ошибка, такие товары считаются обновлёнными \
  Другая ошибка 400 помечает товары только этой пачки, следующая пачка всё равно уходит
- **WB остатки**\
  Неверные названия полей дают 204, но остатки не меняются, поэтому тесты фиксируют точный формат тела запроса
- **Товар без ответа**\
  Если площадка не вернула результат по товару, он считается не обновлённым

## Идемпотентный импорт заказов

Один и тот же заказ можно получить сколько угодно раз, а в базе он окажется один раз и спишет остаток один раз

1. Заказы запрашиваются с момента последнего импортированного минус час (`MARKETPLACE_ORDERS_OVERLAP_MINUTES`) \
   При первом запуске за последние сутки (`MARKETPLACE_ORDERS_LOOKBACK_HOURS`)
2. Заказы сохраняются через `INSERT ... ON CONFLICT (marketplace, external_id) DO NOTHING RETURNING external_id` \
   `RETURNING` возвращает только реально вставленные строки
3. Остаток уменьшается только по новым и не отменённым заказам и только у привязанных товаров,
   не ниже нуля (`GREATEST(quantity - n, 0)`) \
   Позиции без привязки сохраняются в заказе с `product_id: null`
4. После коммита уходит событие `marketplace.orders_imported`: оно сбрасывает кэш товаров и попадает в журнал событий

- **Зачем перекрытие окна**\
  Заказ может появиться в API площадки с задержкой \
  Лишний час назад ничего не стоит (дубли отсекает уникальный ключ, именно идемпотентность делает перекрытие безопасным)
- **Почему отдельная таблица, а не `orders`**\
  У заказа магазина обязательны покупатель, оплата и письма \
  У заказа с площадки покупателя магазина нет, а оплату и доставку ведёт площадка

## Запуск по расписанию

Синхронизация запускается asyncio циклом в lifespan приложения раз в `MARKETPLACE_SYNC_INTERVAL` секунд (по умолчанию 300) \
`0` выключает расписание, остаётся ручной запуск

- **Advisory lock**\
  У uvicorn несколько воркеров, и цикл крутится в каждом \
  `pg_try_advisory_lock` на отдельном соединении в режиме AUTOCOMMIT пускает синхронизацию только в один воркер,
  остальные пропускают прогон \
  Ручной запуск во время работающей синхронизации получает 409 \
  Если процесс упал, PostgreSQL сам снимает блокировку вместе с соединением
- **Порядок**\
  Сначала импорт заказов, потом выгрузка остатков (продажа на Ozon уменьшает остаток в магазине,
  и WB сразу получает правильное число)
- **Без долгих транзакций**\
  Состояние читается в одной короткой сессии, потом идут запросы к API, результат пишется в новой сессии \
  Соединение из пула не простаивает открытым пока площадка отвечает с повторами

**Цена решения:** синхронизация живёт в процессе API \
Если она станет тяжёлой, тот же `MarketplaceSyncRunner` переносится в отдельный воркер без изменений в сервисе

## Метрики

- `sfmshop_marketplace_requests_total`: запросы к API площадок, `ok`, `error` (4xx) и `unavailable` (после всех повторов)
- `sfmshop_marketplace_sync_runs_total`: запуски по площадке и операции (`push`, `orders`), исход `ok`, `partial` или `error`
- `sfmshop_marketplace_sync_duration_seconds`: длительность синхронизации
- `sfmshop_marketplace_items_total`: отправленные позиции, `stock` или `price`, `updated` или `failed`
- `sfmshop_marketplace_orders_total`: заказы `imported` и `duplicate`

## Ограничения

- Не запускалось на реальном кабинете продавца
- Только FBS (склад продавца): один склад на площадку из настроек
- Если заказ отменили после импорта, остаток не возвращается: изменения статуса после импорта не отслеживаются
- У WB результат загрузки цен (например, карантин цены) виден только в детализации загрузки, она не опрашивается
- Цена на WB округляется до целых рублей: дробную цену WB не принимает

## Возможное развитие

- Обновлять статусы импортированных заказов и возвращать остаток при отмене
- Опрашивать детализацию загрузки цен WB и записывать ошибки карантина в `last_error`
- Пуш уведомления Ozon о новых отправлениях вместо опроса
- Несколько складов на площадку
