# Хранилища данных SFMShop

В проекте три хранилища, у каждого своя задача:
- PostgreSQL хранит бизнес-данные
- Redis ускоряет чтение
- MongoDB хранит журнал бизнес-событий

Документ описывает, что где лежит, почему выбрано именно так и как база будет масштабироваться

## Что где хранится

| Хранилище | Данные | В проекте |
| --- | --- | --- |
| PostgreSQL | `users`, `products`, `orders`, `order_items`, `reviews` | есть, схема в `src/database/models.py`, миграции Alembic |
| Redis | кэш каталога, пользователей и заказов | есть |
| Redis | сессии `session:{token}` | методы в `CacheService` есть, но не используются: авторизация на JWT без серверных сессий |
| MongoDB | журнал событий `events`: создание, изменение и удаление товаров, пользователей и заказов | есть, пишет консьюмер `event_log_queue`, читает админ через `GET /v1/events/` |

Таблица `reviews` есть в схеме, но API для отзывов пока нет

## Почему PostgreSQL

Заказ списывает деньги с баланса и уменьшает остаток товара, и это должно произойти целиком или не произойти вовсе\
Поэтому для бизнес данных нужна реляционная СУБД:

- ACID-транзакции: `create_order` блокирует пользователя и товары через `SELECT ... FOR UPDATE` и меняет их в одной транзакции
- Связи и ограничения: внешние ключи с каскадным удалением, `CHECK` на рейтинг отзыва
- JOIN и агрегаты для отчётов
- Деньги в `DECIMAL(10, 2)`, без ошибок округления float
- Встроенная репликация

## Почему Redis

- Данные в памяти: ответ из кэша быстрее запроса в БД
- TTL у ключей: устаревший кэш удаляется сам
- снимает с PostgreSQL самые частые чтения: список товаров и карточку товара

Redis здесь производный слой: источник правды всегда PostgreSQL, потерю кэша приложение переживает

## Почему MongoDB для журнала событий

У событий разная структура: в `order.created` есть заказ, покупатель и товары, в `product.updated` только товар\
Документная БД хранит каждое событие как есть, вместе с исходным телом в поле `payload`, без миграций при появлении новых полей\
Журнал только дописывается и читается по времени, транзакции и JOIN ему не нужны, а PostgreSQL с бизнес-данными не нагружается

Устройство:

- **Запись через очередь**\
  Консьюмер `event_log_queue` получает все восемь событий из RabbitMQ и пишет их в коллекцию `events`.\
  Запрос пользователя не ждёт Mongo, а падение Mongo не ломает заказы: события ждут в очереди и уходят в `event_log_queue.error` после 3 попыток
- **Идемпотентность**\
  `_id` документа это `message_id` сообщения, запись через upsert с `$setOnInsert`.\
  Повторно доставленное сообщение не создаёт дубль
- **Документ**\
  `event`, `occurred_at`, списки `product_ids`, `user_ids`, `order_ids` и исходный `payload`
- **Индексы**\
  по времени, по типу события и по каждому списку id; поиск «все события заказа 7» идёт по multikey-индексу
- **Срок хранения**\
  TTL-индекс удаляет события старше `EVENT_LOG_TTL_DAYS` (90 дней).\
  Индексы создаются при старте; чтобы поменять срок у существующего индекса, нужен `collMod` или пересоздание индекса
- **Драйвер**\
  асинхронный API PyMongo (`AsyncMongoClient`) вместо устаревшего Motor, таймаут выбора сервера 2 секунды

В событиях пока нет того, кто совершил действие: сервисы получают id сущностей, но не текущего пользователя\
Следующий шаг для полноценного аудита: передавать `actor_id` из роутеров в сервисы и в тело события

Логи приложения в Mongo не пишутся: в контейнерах их принято отдавать в stdout сборщику (Loki, ELK)

## Сравнение

| Критерий | PostgreSQL | Redis | MongoDB |
| --- | --- | --- | --- |
| Модель | реляционная | key-value | документная |
| Схема | строгая | нет | гибкая |
| Транзакции | полные ACID | ограниченные | ограниченные |
| Скорость | средняя | очень высокая | высокая |
| Масштабирование | реплики, вертикальное | кластер | шардирование из коробки |
| Роль в проекте | основные данные | кэш, счётчики rate limit | журнал событий |

## Потоки данных

Чтение:

```text
Клиент → API → Redis → (hit) → ответ
                     → (miss) → PostgreSQL replica → Redis → ответ
```

Запись:

```text
Клиент → API → PostgreSQL primary → commit → событие в RabbitMQ → консьюмеры: сброс кэша в Redis, запись в журнал MongoDB
```

Подробно про события в [message_queue_architecture.md](message_queue_architecture.md)

## Репликация

Primary принимает запись, реплики отдают чтение\
В коде это две сессии: `get_write_session` для primary и `get_read_session` для реплики

| Операция | БД |
| --- | --- |
| создание и удаление заказа, изменение баланса | primary |
| изменение товаров и пользователей | primary |
| каталог, профили, история заказов | реплика |
| инструменты ИИ-ассистента | реплика |

В Docker Compose обе сессии смотрят на одну и ту же БД, отдельная реплика появляется при развёртывании

Плюсы:

- чтение масштабируется добавлением реплик
- аналитические запросы не нагружают primary
- при падении primary реплику можно повысить

Минусы:

- реплика отстаёт от primary: пользователь создал заказ, сразу открыл список и может его не увидеть.\
  Решение: читать после записи из primary там, где это критично
- код должен явно разделять запись и чтение

## Шардирование

Шардирование делит данные между несколькими базами, например `users` и `orders` по `user_id`\
Нужно, когда не хватает ни реплик, ни вертикального масштабирования, а нагрузка на запись продолжает расти

Цена высокая:

- JOIN между шардами невозможен или дорог
- нужна маршрутизация запросов по ключу шарда
- миграции и транзакции через несколько шардов сложнее

Для SFMShop порядок такой: одна база → реплики для чтения → шардирование только при реальной нагрузке на запись\
Текущая оценка нагрузки в [hosting_strategy.md](hosting_strategy.md)

## Компромиссы

- **Согласованность:** PostgreSQL строго согласован, кэш и реплики согласованы в конечном счёте.\
  Кэш сбрасывается событием после коммита, в худшем случае устаревает на TTL (15 минут)
- **Сложность:** три хранилища и брокер нужно поднимать, мониторить и бэкапить
- **Производительность:** быстрые ответы из кэша и разгрузка primary стоят накладных расходов на инвалидацию и репликацию
