# Гибридная архитектура базы данных для SFMShop

## 1. Обзор

В проекте SFMShop используется гибридная архитектура хранения данных, основанная на использовании нескольких типов баз данных:

- PostgreSQL основная реляционная БД
- Redis кэш, сессии
- MongoDB логи

Цель архитектуры обеспечить:
- высокую производительность
- масштабируемость
- надежность данных

---

# 2. Распределение данных по БД

## 2.1 PostgreSQL (основные данные)

### Хранит:
- users (пользователи)
- products (товары)
- orders (заказы)
- order_items (позиции заказов)
- reviews (отзывы)

### Причины выбора:
- строгая схема данных
- связи между таблицами
- транзакции (ACID)
- критичность данных (деньги, заказы)

---

## 2.2 Redis (кэш)

### Хранит:
- кэш:
  - списки товаров (`products:*`)
  - пользователи (`user:{id}`)
  - заказы (`user_orders:{id}`)
  - ...
- сессии пользователей (`session:{token}`)

### Причины выбора:
- высокая скорость
- поддержка TTL
- разгрузка PostgreSQL

---

## 2.3 MongoDB (логи и аналитика)

### Хранит:
- логи ошибок
- логи HTTP
- события системы
- действия пользователей

### Причины выбора:
- гибкая схема
- разные структуры логов
- удобные агрегаты
- горизонтальное масштабирование

---

# 4. Поток данных

## 4.1 Чтение данных

1. Клиент → Запрос FastAPI
2. Проверка кэша (Redis)
3. Если есть → вернуть из Redis
4. Если нет:
   - запрос в PostgreSQL (Реплика)
   - сохранить в Redis
   - вернуть клиенту

---

## 4.2 Запись данных

1. Клиент → Запрос FastAPI
2. Запись в PostgreSQL (Основная БД)
3. Инвалидация кэша (Redis)
4. Логирование события в MongoDB

---

## 4.3 Логирование

1. Генерируется событие
2. Запись в MongoDB
3. Используется для:
   - мониторинга
   - аналитики
   - отладки

---

# 5. Связи между БД

- PostgreSQL → источник данных
- Redis → производный слой (кэш)
- MongoDB → независимое хранилище событий (логи)

Связи:
- Redis кэширует данные из PostgreSQL
- MongoDB получает события из логики программы (не из PostgreSQL напрямую)

---

# 6. Обоснование выбора

## Почему PostgreSQL:
- необходима строгая консистентность
- сложные связи между сущностями
- транзакции (особенно для финансовых операций)

## Почему Redis:
- ускорение API
- уменьшение нагрузки на БД
- быстрый доступ к данным

## Почему MongoDB:
- гибкость структуры логов
- удобная агрегация
- масштабируемость

---

# 7. Компромиссы

## 7.1 Eventual Consistency

- кэш может быть устаревшим
- реплики могут отставать

Решение:
- инвалидация кэша
- чтение из основной БД при необходимости

---

## 7.2 Сложность

- больше компонентов - сложнее поддержка
- требуется мониторинг

---

## 7.3 Производительность

Плюсы:
- быстрые ответы (Redis)
- распределение нагрузки (Реплика)

Минусы:
- накладные расходы на синхронизацию

---

## 7.4 Консистентность

- PostgreSQL строгая согласованность
- Redis слабая согласованность
- MongoDB слабая согласованность

---

# 8. Преимущества архитектуры

- высокая производительность
- масштабируемость
- гибкость
- устойчивость к нагрузкам

---

# 9. Недостатки

- сложность реализации
- необходимость инвалидации кэша
- возможная рассинхронизация данных
- дополнительные ресурсы

---

# 10. Вывод

Гибридная архитектура SFMShop позволяет:

- эффективно обрабатывать большие нагрузки
- разделить ответственность между БД
- использовать сильные стороны каждой технологии

Подход:
- PostgreSQL для критичных данных
- Redis для ускорение
- MongoDB для аналитики и логов

Это обеспечивает баланс между:
- производительностью
- консистентностью
- масштабируемостью
