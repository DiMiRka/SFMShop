# Системный дизайн SFMShop

Документ описывает целевую архитектуру и то, как она соотносится с текущим кодом\
Целевые RPS здесь учебные ориентиры, расчёт нагрузки для проекта лежит в [hosting_strategy.md](hosting_strategy.md)

## Компоненты

| Компонент | Роль | В проекте |
| --- | --- | --- |
| API (FastAPI + Uvicorn) | HTTP-запросы: auth, users, products, orders, assistant | есть |
| PostgreSQL primary | запись | есть |
| PostgreSQL replica | чтение | есть отдельная сессия, в Docker Compose указывает на ту же БД |
| Redis | кэш | есть |
| RabbitMQ | события для инвалидации кэша и уведомлений | есть |
| MongoDB | журнал бизнес-событий | есть: пишет консьюмер RabbitMQ, читает админ через `/v1/events/` |
| Docker, Docker Compose, Kubernetes | запуск и развёртывание | есть |
| Nginx | балансировщик перед API | нет, в Kubernetes балансирует Service |
| Фоновые воркеры | тяжёлые задачи | нет, консьюмер RabbitMQ работает внутри приложения |

## Масштабирование

### Горизонтальное масштабирование API

```text
Client → Load Balancer → [App 1, App 2, ..., App N]
```

- каждый инстанс stateless
- состояние хранится в PostgreSQL и Redis
- в Kubernetes число подов меняет HPA: от 1 до 5 при загрузке CPU выше 60% (`deploy/k8s/hpa.yaml`)

### Масштабирование базы данных

```text
Write → Primary
Read  → Replica
```

- запись идёт в primary через `get_write_session`
- чтение идёт в реплику через `get_read_session`
- это снимает с primary нагрузку на чтение каталога и заказов

### Вертикальное масштабирование

Больше CPU и RAM для PostgreSQL и Redis, когда горизонтального масштабирования API уже не хватает

## Кэширование

### Что кэшируется

- список товаров: `products:{limit}:{offset}`
- товар: `product:{id}`
- список пользователей и пользователь: `users:{limit}:{offset}`, `user:{id}`
- заказы: `orders:{owner}:{limit}:{offset}`, `order:{id}`

### Стратегия

Cache aside: сначала читаем Redis, при промахе идём в БД и записываем результат в кэш\
TTL по умолчанию 15 минут (`CacheService`, 900 секунд)

### Инвалидация

Сервис после изменения данных публикует событие в RabbitMQ, консьюмер удаляет ключи:

- по конкретному ключу (`product:{id}`, `order:{id}`)
- по паттерну через `SCAN` пачками (`products:*`, `orders:*`)

Подробно в [message_queue_architecture.md](message_queue_architecture.md)

## Балансировка нагрузки

В Kubernetes трафик между подами распределяет Service (`deploy/k8s/service.yaml`)\
При развёртывании на VM без Kubernetes перед инстансами ставится Nginx:

```nginx
upstream backend {
    server app1:8000;
    server app2:8000;
    server app3:8000;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

Алгоритм по умолчанию round-robin, при запросах разной длительности лучше `least_conn`

## Соединения

- пул соединений PostgreSQL (SQLAlchemy + asyncpg)
- один клиент Redis на приложение
- общие клиенты httpx и Claude API создаются в lifespan и переиспользуются

## Метрики производительности

Целевые показатели:

- RPS: старт 500–1000, цель 3000+
- latency: p50 < 50 ms, p95 < 150 ms, p99 < 300 ms

Ожидаемые узкие места:

- база данных
- сетевые вызовы внешних сервисов
- промахи кэша

## Этапы масштабирования

| Этап | Нагрузка | Что нужно |
| --- | --- | --- |
| 1 | до 1000 RPS | 1–2 инстанса API, PostgreSQL, Redis |
| 2 | до 3000 RPS | 3–5 инстансов API, PostgreSQL с репликой, агрессивное кэширование |
| 3 | 5000+ RPS | Kubernetes с HPA, шардирование БД при необходимости, CDN для статики |

## Дополнительные улучшения

| Улучшение | Состояние                                                                                                                                                                                        |
| --- |--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Rate limiting | есть: slowapi на вход (по IP) и на ИИ-ассистента (по пользователю), счётчики в Redis; при недоступном Redis лимиты временно считаются в памяти пода                                              |
| Health checks | есть: `/health/live` и `/health/ready`, пробы Kubernetes                                                                                                                                         |
| Circuit breaker | нет; клиент курсов валют и публикация событий делают повторы с экспоненциальной задержкой                                                                                                        |
| Очереди | есть RabbitMQ; email и платежи пока только в плане                                                                                                                                               |
| Логирование | есть: Loguru, структурированные поля, Sentry при заданном `SENTRY_DSN`                                                                                                                           |
| Метрики | есть: Prometheus на отдельном порту 9100 (HTTP, кэш, события, заказы, ИИ-ассистент) и правила алертов в `deploy/prometheus/alerts.yml`<br/> Дашборд Grafana «Состояние сервиса» в Docker Compose |

## Итог

SFMShop масштабируется горизонтально за счёт stateless API, снижает нагрузку на БД кэшем и репликой для чтения,
а инвалидацию кэша делает через события RabbitMQ\
Состояние видно по метрикам Prometheus и пробам здоровья\
Следующий шаг: вынос консьюмера в отдельный deployment и уведомления по алертам (Alertmanager)
