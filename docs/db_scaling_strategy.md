# Стратегия масштабирования базы данных для SFMShop

# 1. Стратегия репликации

## 1.1 Что такое репликация

Репликация это процесс копирования данных с основной базы данных (Primary) на одну или несколько реплик (Replica)

- **Primary** - обрабатывает запись (INSERT/UPDATE/DELETE)
- **Replica** - используется для чтения (SELECT)

---

## 1.2 Когда использовать репликацию

Репликация применяется если:

- Высокая нагрузка на чтение
- Много SELECT запросов
- Требуется отказоустойчивость
- Аналитические запросы нагружают основную БД

### В SFMShop:

Репликация подходит для:
- Просмотра каталога товаров
- Получения информации о пользователях
- Истории заказов
- Отчетов и аналитики

---

## 1.3 Преимущества

- Увеличение производительности чтения
- Снижение нагрузки на основную БД
- Возможность масштабирования чтения
- Повышение отказоустойчивости

---

## 1.4 Недостатки

- Задержка репликации
- Данные могут быть неактуальны
- Усложнение архитектуры
- Необходимость разделения read/write логики

---

## 1.5 Пример для SFMShop

| Операция              | Используемая БД |
|----------------------|----------------|
| Создание заказа      | Primary         |
| Обновление баланса   | Primary         |
| Получение товаров    | Replica         |
| Получение заказов    | Replica         |

---

# 2. Стратегия шардирования

## 2.1 Что такое шардирование

Шардирование это разделение данных на несколько баз данных (шардов)

Каждый шард содержит часть данных

---

## 2.2 Когда использовать шардирование

Шардирование необходимо если:

- База данных стала слишком большой
- Высокая нагрузка на запись
- Вертикальное масштабирование больше не помогает
- Требуется распределение нагрузки

---

## 2.3 Преимущества

- Горизонтальное масштабирование
- Увеличение производительности записи
- Распределение нагрузки

---

## 2.4 Недостатки

- Сложная реализация
- Сложные JOIN между шардами
- Требуется логика маршрутизации
- Усложнение миграций

---

## 2.5 Пример для SFMShop

Шардирование можно применить к:

- таблице users
- таблице orders


---

# 3. Компромиссы и ограничения

## 3.1 Eventual Consistency (слабая согласованность)

- Реплики могут отставать от основной БД
- Пользователь может не увидеть изменения сразу

### Пример:
Пользователь создал заказ → сразу смотрит список заказов → заказ может не отображаться

### Решение:
- Читать после записи из Primary
- Инвалидация кэша

---

## 3.2 Сложность настройки

| Механизм      | Сложность |
|--------------|----------|
| Репликация   | Средняя  |
| Шардирование | Высокая  |

Требуется:
- Мониторинг
- Настройка инфраструктуры
- Обработка ошибок

---

## 3.3 Производительность

### Репликация:
- Улучшает чтение
- Не влияет на запись

### Шардирование:
- Улучшает чтение и запись
- Требует дополнительной логики

---

# 4. Вывод

- Репликация - первый шаг к масштабированию
- Шардирование - решение для больших нагрузок
- Необходимо учитывать компромиссы:
  - Простота vs масштабируемость
  - Консистентность vs производительность

Для SFMShop:
- Начинать с простой архитектуры
- Добавлять репликацию при росте нагрузки
- Использовать шардирование только при необходимости
